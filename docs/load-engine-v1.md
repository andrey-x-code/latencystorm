# Генератор нагрузки одного агента

Этап 4 добавляет автономный движок в `src/load-agent/internal/engine`. Он не зависит от gRPC, Kafka или PostgreSQL. Для локальной проверки агент принимает JSON-конфигурацию и выводит измерения в stdout в формате NDJSON.

## Локальный запуск

Поднимите Demo Target из корня репозитория:

```powershell
docker compose --env-file deploy/compose/.env.example -f deploy/compose/compose.yaml up --build -d demo-target
```

При установленном Go 1.26.10 запустите агент из каталога `src`:

```powershell
go run ./load-agent --local ../examples/load-agent/local.json
```

Пример задаёт 20 RPS на 3 секунды к `http://127.0.0.1:8083/`. Для завершения окружения:

```powershell
docker compose --env-file deploy/compose/.env.example -f deploy/compose/compose.yaml down
```

Без установки Go можно собрать образ агента:

```powershell
docker build -f src/load-agent/Dockerfile -t latencystorm-load-agent:stage-04 src
docker run --rm --mount "type=bind,source=$((Get-Location).Path)/examples/load-agent,target=/config,readonly" latencystorm-load-agent:stage-04 --local /config/local.json
```

В контейнере `127.0.0.1` относится к самому агенту. Для Demo Target на Windows-хосте укажите в копии конфигурации `http://host.docker.internal:8083/`. При запуске в общей Docker-сети используйте имя сервиса и его внутренний порт. Для остановки контейнера передайте SIGTERM, например `docker stop --time 5 <container>`; период ожидания должен превышать `drainTimeoutMs`.

## Конфигурация и ограничения

| Поле | Значение и границы |
| --- | --- |
| `method` | GET, POST, PUT, PATCH, DELETE или HEAD |
| `url` | Абсолютный HTTP/HTTPS URL без credentials и fragment |
| `headers` | До 100 статических заголовков; имя до 256 байт, значение до 8192 байт |
| `body` | Строка UTF-8 размером до 1 MiB; по умолчанию пустая |
| `rps` | Целое число 1..1 000 000 |
| `durationMs` | Длительность генерации 1..86 400 000 мс |
| `requestTimeoutMs` | Полный таймаут запроса, включая тело, 1..300 000 мс |
| `maxConcurrency` | Максимум выполняющихся запросов, 1..100 000 |
| `maxResponseBodyBytes` | Лимит чтения тела, 1..16 MiB |
| `drainTimeoutMs` | Ожидание текущих запросов после остановки генерации, 1..300 000 мс |

Неизвестные поля и несколько JSON-документов отклоняются. Поля управления HTTP-транспортом (`Content-Length`, `Transfer-Encoding`, `Connection`, `Trailer`, `Upgrade`) запрещены. При ошибке конфигурации процесс завершается с кодом 2; при ошибке чтения файла или вывода — с кодом 1. Успешное завершение, включая ручную остановку, возвращает 0. HTTP-ошибки и таймауты являются результатами измерений, а не ошибкой самого процесса.

## Расписание и остановка

Слоты привязаны к монотонному времени начала: `start + k/RPS`. План рассчитывается целочисленно с округлением вверх; скорость ответа сервера не сдвигает сетку. При опоздании старые слоты учитываются как `skipped`; текущий слот запускается только при свободном месте. Очереди догоняющих запросов нет. Верхний предел RPS является границей конфигурации, а не обещанием достижимой производительности.

SIGINT/SIGTERM или отмена контекста прекращает новые старты. Текущие запросы могут завершиться за `drainTimeoutMs`; затем их контексты отменяются. Движок дожидается завершения своих горутин. Остановка до начала возвращает нулевые счётчики и интервал нулевой длины.

HTTP-клиент переиспользует соединения, работает по HTTP/1.1, не следует redirects и не выполняет прикладных повторов. Неповторяемое тело запроса без `GetBody`, включая запросы без полезной нагрузки, запрещает прозрачный retry на переиспользованном соединении. Автоматическая декомпрессия отключена; лимит применяется к полученным байтам. Тело ответа не сохраняется: оно читается до EOF или лимита плюс один байт для обнаружения превышения.

## Измерения

Каждая строка `type=interval` содержит дельты закрытого секундного интервала. Последняя строка `type=summary` содержит полный план, итоговые счётчики, фактическое окно генерации, признак ручной остановки и `final` с оставшимися дельтами после drain. Последний интервал может иметь нулевую длину. UTC-границы вычисляются от исходного времени и монотонных смещений.

`scheduled = started + skipped`; после drain `started = finished`. HTTP 4xx/5xx входят в полные HTTP-ответы и отдельно в `httpErrors`. Транспортные ошибки, таймауты, отмены и превышение лимита тела учитываются раздельно. Статус считается только после полного чтения ответа. HTTP latency и failure latency используют 20 фиксированных корзин `latency-us-v1`, включительные границы в микросекундах и отдельный overflow, совместимые с [правилами измерений](measurements-v1.md).

Очередь закрытых интервалов ограничена 16 элементами. Медленный потребитель не блокирует генератор: потеря интервала устанавливает `measurementsLost`. Итоговые счётчики продолжают учитывать все исходы; потерянный временной ряд не восстанавливается. Локальный NDJSON — диагностический формат, его нельзя публиковать как Kafka `ResultBatch`. Передача нормативных protobuf-пакетов относится к этапу 5.

## Проверки

Из корня репозитория:

```powershell
docker build -f tests/load-engine/Dockerfile.verify --target export --output type=local,dest=.artifacts/load-engine .
```

Проверка использует Go 1.26.10 и Python 3.13.9: проверяет gofmt, отсутствие изменений `go mod tidy`, выполняет `go vet`, модульные тесты, race detector и HTTP-тесты с тегом `integration`. Затем собирает агент и Demo Target и запускает smoke-сценарии успешных ответов, таймаутов, нехватки конкурентности и SIGTERM.

Модульные тесты с `testing/synctest` проверяют сетку стартов при разной скорости ответов, задержку пробуждения без всплеска, отмену до старта и во время работы, drain, переполнение очереди, арифметику суточного плана и границы гистограммы. HTTP-тесты проверяют redirects, EOF на границе лимита, превышение лимита, обрыв тела, повторное использование соединения и отсутствие retry при обрыве reused connection.

На локальном Docker Linux стенде smoke-проверка при 20 RPS за 2 секунды получила 40 полных ответов без пропусков. При задержке цели 200 мс и таймауте 50 мс получены 40 таймаутов. При задержке 200 мс и конкурентности 1 получены 8 стартов и 32 пропуска. Эти результаты подтверждают поведение на малой нагрузке; предел производительности и распределённая генерация на этом этапе не измерялись.
