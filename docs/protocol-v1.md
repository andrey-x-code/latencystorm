# Протокол выполнения v1

Нормативные типы находятся в contracts/proto/latencystorm/v1. Слова «должен» и «нельзя» задают требования к будущим реализациям сервисов. Этот этап фиксирует контракты, но не запускает генератор и не реализует хранилище.

## Сущности и входные ограничения

Все runId, scenarioId, assignmentId, sessionId и commandId — UUID в нижнем регистре с дефисами. agentId — стабильная строка конфигурации длиной 1–128 ASCII-символов из [A-Za-z0-9._-], сохраняется после перезапуска агента. Новый процесс создаёт новый sessionId. Пользовательское имя сценария — 1–200 символов, диагностическое detail — до 1024 байт без чувствительных данных. Временные метки — RFC 3339 UTC / protobuf Timestamp; интервалы ниже полуоткрытые.

- **Scenario** — изменяемое определение HTTP-запроса с положительной revision. Изменение увеличивает revision; scenarioId в definition совпадает с внешним scenarioId. createdAt неизменен, updatedAt отражает изменение.
- **Run** — UUID, неизменяемый snapshot определения на момент запуска, состояния и времена. Изменение или удаление исходного сценария не меняет запущенный тест. До выбора старта scheduledStartAt отсутствует; generationStoppedAt и finishedAt отсутствуют до соответствующих событий.
- **Agent** — стабильный agentId, текущая сессия, доступность и одно активное назначение. Offline означает потерю сессии, но не доказанную остановку нагрузки. Idle — свободен, Reserved — участвует в подготовке, Busy — получил Start. Не освобождайте резерв только из-за разрыва потока.
- **Assignment** — неизменяемое соответствие runId + assignmentId + agentId и положительная assignedRps. Все команды и результаты адресуются этому назначению; одно назначение нельзя переносить другому агенту. Полный snapshot передаётся в Prepare, а собственная доля RPS хранится отдельно.

ScenarioSnapshot содержит HTTP method как верхнерегистровый токен; абсолютный http/https URL без userinfo и fragment; уникальные без учёта регистра имена headers и список их значений без CR/LF; необязательное бинарное body (в JSON base64). Запрещены ручные Host, Content-Length и hop-by-hop headers; транспорт вычисляет их сам. Отсутствующее и пустое body различаются через optional bytes. Максимум тела запроса — 1 MiB, URL — 8192 байт, суммарных заголовков — 64 KiB, значений — 256. Проверять до резервирования агентов. Значения request и заголовков не попадают в логи.

MVP принимает целые totalRps 1–1 000 000, durationMs 1–86 400 000, requestTimeoutMs и drainTimeoutMs 1–300 000, maxConcurrencyPerAgent 1–100 000, maxResponseBodyBytes 1–16 777 216. Это границы валидации, а не обещание производительности. Все поля snapshot обязательны, revision > 0. Нулевые значения enum недопустимы, кроме явно документированных исключений. На платформе один активный Run, на агенте одно Assignment. Сумма assignedRps равна totalRps; число агентов не больше totalRps, доли не нулевые. Остаток распределяется по возрастанию agentId, первым r агентам выдаётся q+1 при totalRps=q*n+r.

## Состояния

| Объект | Допустимые переходы |
| --- | --- |
| Run | Preparing → Running, Stopping или Failed; Running → Stopping; Stopping → Completed, Stopped или Failed |
| Assignment | Preparing → Ready или Stopping; Ready → Scheduled или Stopping; Scheduled → Running или Stopping; Running → Stopping; Stopping → Completed, Stopped или Failed |
| Report | Collecting → Complete или Incomplete |

При ошибке подготовки Run может сразу стать Failed, но блокировка новых запусков остаётся до очистки резервов и безопасной остановки всех назначений. Run становится Running в назначенный момент старта; Assignment — после фактического старта генератора. Stopping включает ожидание текущих запросов. По естественному окончанию длительности итог Completed; по ручной остановке — Stopped; по инфраструктурной ошибке — Failed. Повторный запрос Stop к терминальному Run безопасно возвращает его состояние и не изменяет итог. Терминальные состояния неизменяемы.

Причина Failed обязательна и берётся из FailureReason: PreparationRejected, PreparationTimeout, AgentLost, LeaseExpired, CoordinatorRestarted, InternalError, ProtocolViolation. Для остальных состояний причина Unspecified. HTTP 4xx/5xx, таймауты и сетевые ошибки тестируемого сервиса — результаты измерения, сами по себе они не переводят Run в Failed. Отказ регистрации или неверная команда не создают Run. Для подготовки Assignment может перейти из Preparing/Ready в Stopping и затем Failed с причиной ошибки подготовки; остановка до Start даёт Stopped, без измерений.

При конкурирующих событиях решение принимает координатор под блокировкой/транзакцией: до терминального состояния любая инфраструктурная ошибка имеет приоритет над ручной остановкой, ручная остановка — над естественным завершением; среди ошибок сохраняется первая зафиксированная. После терминального состояния поздние сообщения не переписывают результат. finishedAt означает, что локальные запросы завершены/отменены; публикация результата и полнота отчёта отслеживаются отдельно.

Отчёт создаётся как Collecting при принятии манифеста; результат до манифеста сохраняется ограниченно в ожидании него и никогда не считается полным сам по себе. Complete требует манифеста и всех последовательностей 1..finalSequence каждого ожидаемого назначения, одного корректного финального summary, корректных инвариантов и отсутствия потерь. Complete возможен для Failed/Stopped Run, если измерения полностью доставлены. Завершение Run и готовность отчёта независимы. Неизвестные назначения из пакетов не добавляются в ожидаемый набор.

Если нарушены инварианты, есть потери либо по resultDeadline отсутствуют манифест/пакеты/финальный пакет, состояние Incomplete с одной или несколькими ReportIncompleteReason. InvalidBatch, MeasurementsLost — необратимые причины. После дедлайна поздние корректные пакеты можно сохранить для диагностики, но терминальную полноту не повышать. Отсутствие манифеста определяется для результата-сироты по первому получению + 5 минут; такого отчёта нельзя выдавать за подтверждённый запуск. Для неизвестной версии, которую невозможно привязать к runId, сохраняется карантин и метрика, а ожидаемый Run обнаружит недостачу по дедлайну.

## Регистрация и поток управления

AgentControl.Connect — двунаправленный упорядоченный gRPC stream. Агент первым отправляет RegisterAgent с protocolVersion=1, agentVersion, agentId и sessionId в конверте. Все следующие сообщения сохраняют те же идентификаторы. До RegistrationAccepted никаких заданий не исполняется. Сервер отвечает с тем же sessionId и уникальным commandId. Только один поток может владеть agentId; конфликтующая активная сессия отклоняется ALREADY_EXISTS, неподдерживаемая версия — FAILED_PRECONDITION, неверный конверт — INVALID_ARGUMENT. Сетевые отказы возвращают UNAVAILABLE, дедлайны RPC — DEADLINE_EXCEEDED. В локальном MVP соединение без прикладной авторизации, только в тестовой сети; TLS-конфигурация не меняет контракт.

Базовые интервалы: heartbeat 1000 ms, lease 5000 ms, потеря heartbeat после 3000 ms, подготовка 10000 ms, запас старта 2000 ms. Часы хостов должны быть синхронизированы, допустимое смещение ≤100 ms; значение coordinatorTime позволяет агенту отклонить подготовку при превышении. Это эксплуатационное требование: точная синхронизация времени протоколом не обеспечивается.

В idle heartbeat содержит пустой assignmentId и Unspecified; для активного назначения — его ID и текущее состояние. Координатор измеряет отсутствие heartbeat своими монотонными часами, sentAt нужен для диагностики. Переподключение: bounded exponential backoff 100 ms..5 s с jitter, не бесконечная очередь сообщений. Новый поток не даёт права возобновить старое назначение; до истечения старой аренды/подтверждения остановки агент не считается свободным. Новая регистрация с тем же sessionId разрешается лишь после закрытия предыдущего потока и безопасного завершения старой работы. Завершённое назначение не запускается повторно после reconnect.

## Успешный запуск

1. Координатор сохраняет Run Preparing с копией ScenarioSnapshot и атомарно резервирует свободных агентов. Для каждого создаёт уникальное Assignment и отправляет PrepareAssignment с дедлайном. Агент проверяет входные ограничения, свободные ресурсы, часы и доступность публикации результатов, резервирует локальные ресурсы и отвечает AssignmentReady с prepareCommandId. Генерация ещё не идёт.
2. После готовности всех назначается общее startAt с запасом. RunManifest содержит snapshot, полный ожидаемый набор назначений, план запросов и жёсткий resultDeadline = startAt + durationMs + drainTimeoutMs + 30000 ms. Координатор вызывает ResultsIngestion.PutRunManifest с RPC deadline 5 s и дожидается подтверждения долговременного сохранения. Повтор с идентичным содержимым возвращает тот же ACK; другое содержимое для того же runId — ALREADY_EXISTS. Сбой подтверждения до startAt отменяет подготовку.
3. Только после ACK манифеста координатор посылает StartAssignment всем агентам: те же runId/assignmentId, startAt, leaseExpiresAt и leaseSequence=1. Первоначальная аренда должна покрывать старт: expiresAt=startAt+5000 ms. Поздний Start (получен в startAt или позже) отклоняется DeadlineExceeded; координатор прекращает запуск целиком. Уже стартовавшие агенты останавливаются командой Stop или по аренде; атомарный одновременный старт при сетевом сбое не обещается.
4. Агент один раз преобразует startAt в локальный монотонный дедлайн, ждёт его, отправляет AssignmentStarted с actualStartAt, генерирует фиксированную долю RPS. Задержка локального планировщика после принятого Start учитывается пропусками; длительность не продлевается. Lease возобновляется примерно раз в секунду.
5. Агент публикует секундные дельты и финальную дельту с summary, прекращает нагрузку по длительности и ограниченно ожидает запросы. AssignmentFinished по gRPC содержит состояние, финальный sequence, sticky measurementsLost и факт подтверждения публикации final Kafka-брокером. Подтверждение брокера ещё не означает сохранение Results Service.
6. Координатор сохраняет терминальный Run и идемпотентно отправляет RunFinalization. Точный повтор безопасен, конфликт — ALREADY_EXISTS; неизвестный runId — NOT_FOUND; нетерминальное состояние — INVALID_ARGUMENT. FinalizeRun не является условием Complete: после сбоя координатора манифест и финальные пакеты должны быть достаточны для оценки полноты. Если агент не завершился, координатор применяет правила потери связи.

RunManifest неизменяем после ACK. Если запуск отменён после манифеста, каждое подготовленное назначение должно выпустить пустой финальный пакет (sequence=1, нулевые счётчики/гистограммы, actualStartAt отсутствует, duration=0). Если агент потерян, отсутствие final будет отражено как Incomplete; координатор не создаёт измерения за него. Отмена до создания манифеста освобождает все резервы и не запускает генерацию.

## Идемпотентность, остановка, аренда

CommandId уникален в сессии; точный повтор возвращает прежний ACK/событие и не выполняет действие заново. Тот же ID с другим содержимым — ConflictingCommand. Повторный Prepare для того же назначения и snapshot возвращает готовность только пока назначение Ready; после Start не возвращает его в Ready. Повторный Start с теми же параметрами не создаёт второй генератор и не сдвигает время; уже известный завершённый Start возвращает сохранённое терминальное событие. Новые Start/Prepare для старого терминального назначения отклоняются StaleAssignment. Повтор Stop безопасен; для активного назначения повтор возвращает состояние, для терминального — сохранённое AssignmentFinished. Сохраняйте tombstone терминальных assignmentId до конца сессии; при достижении лимита 10000 завершённых назначений агент должен завершить idle-сессию и создать новую, а не забывать защиту от дублей в активной сессии.

Проверяйте sessionId, runId и assignmentId до выполнения команды. Для другого активного назначения — Busy; для старого/неизвестного — StaleAssignment. Подготовка с тем же assignmentId и изменёнными параметрами — ConflictingCommand. Это проверка протокола, не общий механизм очереди задач.

Stop до startAt отменяет таймер старта, не выполняет ни одного запроса и публикует пустой final. Stop во время генерации прекращает новые слоты немедленно; поздние слоты после фактической остановки не входят в scheduled. In-flight запросы завершаются до меньшего из request deadline и drain deadline; остаток отменяется и учитывается как Cancelled. Длительность generationDurationUs измеряется монотонно, ограничена планом и не включает drain. В фазе drain Stop не перезапускает дедлайн и не сбрасывает счётчики. После завершения всех запросов агент выпускает final; завершение доставки имеет отдельный лимит 30 s.

RenewLease содержит возрастающий leaseSequence и expiresAt. Старые sequence не продлевают работу; одинаковый sequence с другим expiresAt — ошибка. Агент принимает только аренду своего назначения до истечения предыдущей. Для защиты от задержанных команд срок вычисляется как min(expiresAt-receiveUtc,5000 ms) и один раз привязывается к монотонным часам; nonpositive срок отвергается. Продление не сдвигает startAt и естественный конец генерации. Истёкшее разрешение нельзя оживить: новые запросы прекращаются, итог Failed/LeaseExpired, затем drain и final. Один раз принятый Start содержит первоначальную аренду; отдельный RenewLease до Start запрещён.

Координатор при потере heartbeat фиксирует AgentLost, прекращает продление аренды и отправляет Stop остальным. Нагрузка не перераспределяется. Разрыв потока сам по себе не останавливает монотонный срок аренды. При рестарте координатор помечает нетерминальные Run как Failed/CoordinatorRestarted, сохраняет возможность принять поздние результаты и блокирует новые запуски до подтверждения остановки всех старых назначений либо истечения максимального сохранённого leaseExpiresAt + 100 ms (допуск часов) + drainTimeoutMs. До отправки Start/RenewLease максимальный expiresAt сохраняется в управляющей БД, поэтому рестарт не теряет сведения о выданном разрешении.

Буфер Kafka ограничен 16 MiB или 10000 пакетами, что наступит раньше; размер пакета ≤256 KiB. Генератор никогда не ждёт Kafka. sequence выделяется при формировании пакета, до попытки помещения в очередь; потерянный пакет оставляет разрыв. Повтор отправляет тот же payload с тем же sequence, ключом и timestamp. Повторы ограничены backoff 100 ms..5 s и общим сроком доставки; после переполнения measurementsLost становится sticky и передаётся в следующих пакетах/AssignmentFinished. Финальный пакет резервирует отдельное место в том же лимите памяти; после 30 s недоставленные пакеты отбрасываются с признаком потерь, не возобновляются после перезапуска. Отсутствие final и разрывы обнаруживаются по манифесту/дедлайну. Ошибка генератора может сделать Run Failed; потеря измерений отдельно делает отчёт Incomplete.

## Совместимость

Package latencystorm.v1, protocolVersion=1 и schemaVersion=1 — независимые явные идентификаторы версии. Добавление поля требует обновления всех JSON-потребителей до начала публикации: ProtoJSON-парсеры MVP строгие и отвергают неизвестные поля. Удалённые protobuf-теги и имена резервируются; изменение смысла, единиц, enum, гистограммы или JSON-формы требует новой версии схемы/пакета и стратегии миграции. Не используйте сериализацию System.Text.Json/encoding/json поверх сгенерированных типов: применяется Google.Protobuf.JsonParser/JsonFormatter и protojson.
