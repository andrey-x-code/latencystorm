# Измерения и Kafka-пакеты v1

Нормативный тип — ResultBatch из [results.proto](../contracts/proto/latencystorm/v1/results.proto). Правила жизненного цикла описаны в [protocol-v1.md](protocol-v1.md).

## Передача и валидация

Topic: latencystorm.results.v1. Ключ Kafka — UTF-8 assignmentId. Значение — UTF-8 ProtoJSON ResultBatch, content-type application/json. Имена полей lowerCamelCase, enum — полные строковые имена из .proto; uint64 — десятичные строки, bytes — base64, Timestamp — RFC 3339 UTC. Не преобразовывайте счётчики через float/double. Обычные protobuf defaults могут быть опущены; отсутствие message-полей проверяется отдельно. Пример: [result-batch.v1.json](../contracts/events/examples/result-batch.v1.json).

schemaVersion строго 1; runId, assignmentId, agentId соответствуют манифесту; sequence — положительный uint64. Dedup key: (runId, assignmentId, sequence). Повтор того же ключа и семантически равного сообщения игнорируется; другой payload с тем же ключом — InvalidBatch. Сравнивается разобранное сообщение, а не порядок JSON-свойств. Запись пакета, dedup key и изменение агрегатов — одна транзакция; Kafka offset подтверждается после commit. Нельзя подтверждать больший offset раздела до завершения всех предыдущих сообщений этого раздела.

Повторная доставка сохраняет sequence и содержимое. У нового пакета sequence увеличивается на 1, включая final; переполнение sequence — ошибка генератора. Финальный пакет завершает последовательность: сообщения с sequence выше finalSequence или несколько разных финальных номеров делают отчёт Incomplete. Нельзя путать последний полученный пакет с финальным. Отсутствующий пакет обнаруживается по диапазону 1..finalSequence, даже если final уже получен.

Проверяются обязательные interval, counters, httpLatency, failureLatency и UUID/идентификаторы; isFinal эквивалентен наличию summary. Оба histogram должны иметь известный layoutId и ровно 20 bucketCounts, даже при нулевой выборке. Все счётчики неотрицательны, операции сложения выполняются с проверкой переполнения uint64. HTTP-коды уникальны, от 100 до 599, count > 0; порядок записей незначим. Нераспознанная версия/поле/enum, превышение размера 256 KiB, неверная временная метка, несовместимая гистограмма или нарушенный инвариант — карантин без обновления агрегатов. Для известного Run сохраняется InvalidBatch; неизвестный Run не создаёт полноценный отчёт. Для карантина после долговременного сохранения диагностики offset можно подтвердить, чтобы не блокировать раздел. Реализация этой валидации и карантина относится к этапам сервисов; protobuf-парсер сам не проверяет бизнес-инварианты.

## Расписание и интервалы

Для assignedRps=R плановые слоты k=0,1,... приходятся на startAt+k/R секунд, пока k*1000 < R*durationMs. Полный план равен ceil(R*durationMs/1000), рассчитывается целочисленно без float. scheduled включает только слоты строго до фактического конца генерации. В момент ручной остановки/истечения аренды новые слоты больше не создаются. actualStartAt — время фактического пробуждения генератора; плановая сетка остаётся привязанной к startAt. Задержанные до actualStartAt слоты учитываются как skipped, конец теста не сдвигается.

При пробуждении после нескольких пропущенных слотов все просроченные слоты кроме текущего ближайшего учитываются как skipped; для текущего слота проверяется лимит конкурентности. Нельзя запускать очередь запросов, чтобы догнать график. При нормальной работе RPS не зависит от завершения предыдущих запросов. Из-за округления планов назначений в тестах длительностью не целое число секунд сумма ceil по агентам может отличаться от ceil(totalRps*durationMs/1000); манифест хранит точный plannedRequests каждого назначения, суммарный план — их сумма.

Пакеты содержат дельты, а не накопительные totals. Обычные интервалы привязаны к startAt: [startAt+n секунд, startAt+(n+1) секунд). Время события относит scheduled/started/skipped и завершение запроса в соответствующий интервал; запрос может стартовать в одном пакете, закончиться в другом. Для каждого пакета scheduled=started+skipped, но started=finished требуется только в сумме после drain. Поздний callback учитывается в интервале его обработки один раз, уже отправленный интервал не изменяется. Монотонные часы определяют интервалы; границы UTC вычисляются от исходного startAt, а не от прыгающих системных часов.

При ранней остановке генерации сбор завершений продолжается в фазе drain, где scheduled/started/skipped равны нулю. Неполный последний интервал закрывается после drain; финальный пакет несёт оставшиеся дельты и summary. Если интервал уже отправлен, final имеет нулевую длину [end,end] и нулевые дельты. Последовательные интервалы соприкасаются без перекрытий и пропусков; это проверяется в порядке sequence после доставки всех пакетов. При остановке до Start — единственный final с interval=[generationStoppedAt,generationStoppedAt], нулевыми счётчиками, нулевыми гистограммами и без actualStartAt. В summary finishedAt >= generationStoppedAt, при наличии actualStartAt он не позже generationStoppedAt. Terminal summary может иметь только Completed, Stopped, Failed с согласованной причиной.

## Счётчики и ошибки запросов

- scheduled — учтённые плановые слоты; started — переданные HTTP-клиенту запросы; skipped — не запущенные из-за отставания или лимита конкурентности. После завершения scheduled=started+skipped.
- finished — один терминальный исход на каждый started. После drain sum(started)=sum(finished). Повторная доставка не добавляет исход повторно.
- httpResponses — ответы с полностью прочитанным телом до EOF в пределах лимита; включает HTTP 4xx/5xx. httpErrors — подмножество httpResponses со статусом 400..599. HTTP-коды считаются только для полных ответов. 1xx предварительные ответы не считаются отдельно; 3xx без redirect — завершённый ответ без HTTP-ошибки.
- transportErrors — DNS, connect, TLS, reset, оборванное тело и другие ошибки I/O, не являющиеся отменой или дедлайном. Частично полученный ответ не входит в httpResponses и status counts.
- timeouts — завершение из-за request deadline; cancelled — остановка/отмена владельцем, в том числе по drain deadline. При гонке причин используется первый атомарно зафиксированный терминальный исход.
- responseBodyLimitExceeded — прочитано более maxResponseBodyBytes, чтение прекращено и тело закрыто; это отдельный исход, без статуса в httpStatusCounts. Можно прочитать один дополнительный байт для обнаружения превышения. Ответ ровно лимитного размера с EOF считается полным.

Для каждого пакета finished=httpResponses+transportErrors+timeouts+cancelled+responseBodyLimitExceeded. sum(httpStatusCounts.count)=httpResponses; сумма статусов 400..599 равна httpErrors. httpErrors не добавляется к finished второй раз. Все эти числа — наблюдения клиента, а не гарантированное число запросов, обработанных целевым сервером.

Latency полного HTTP-ответа включает 4xx/5xx; failureLatency содержит длительности transportErrors/timeouts/cancelled/responseBodyLimitExceeded. Начало — фактическая передача HTTP-клиенту, конец — EOF или терминальная ошибка; включает ожидание соединения, DNS/TLS и тело. Пропущенные слоты не имеют latency. Длительности измеряются монотонно и округляются вверх до целой микросекунды; нулевая длительность попадает в первый bucket. Redirect и прикладные retries отключены. Go Transport может прозрачно повторять некоторые запросы на переиспользованном соединении; будущая реализация генератора должна исключить такие повторы (например, передавать непустой неповторяемый Body без GetBody, включая пустой поток для запроса без тела) и проверить поведение на обрыве reused connection. Выбор транспортного приёма не меняет правило: один started означает максимум одну отправку на уровне HTTP.

## Гистограмма latency-us-v1

Границы — включительные верхние пределы в микросекундах:

~~~text
100, 250, 500, 1000, 2500, 5000, 10000, 25000, 50000, 100000,
250000, 500000, 1000000, 2500000, 5000000, 10000000, 30000000,
60000000, 120000000, 300000000
~~~

20 некумулятивных bucketCounts. Bucket 0 содержит [0,100], bucket 1 — (100,250], и т.д. overflowCount — значения >300000000. sum(httpLatency.bucketCounts)+overflowCount=httpResponses. Для failureLatency сумма равна finished-httpResponses. Диапазон не расширяется локально агентом: неизвестный layout не объединяется с v1.

Объединение — поэлементная сумма buckets и overflow при одинаковом layoutId. Для percentile p применяется nearest rank: rank=ceil(p*N), затем первый bucket с накопленной суммой >=rank; выдаётся его верхняя граница и признак приблизительности. Если rank попал в overflow, значение отсутствует и возвращается признак overflow/lowerBoundUs=300000000. При N=0 значение отсутствует, а не 0. p50/p95/p99 основного отчёта рассчитаны только по httpLatency; failureLatency отображается отдельно с явной областью выборки. Сами перцентили агентов не усредняются.

Пример имеет scheduled=5, started=4, skipped=1; полные ответы 200 и 500 длительностью соответственно до 500 и 1000 us, один transportError и один timeout до 500000 us. p50 HTTP=500 us, p95/p99 HTTP=1000 us. Пример пакета не задаёт snapshot запроса.

## RPS и полнота

План и цель берутся из манифеста. Мгновенные RPS стартов/завершений — соответствующие дельты за фактическую длину интервала, не обязательно одну секунду. При нулевой длине интервала RPS отсутствует. Средний RPS стартов = sum(started)/(generationDurationUs/1000000); drain в знаменатель не входит. При ранней остановке до Start RPS отсутствует. Для нескольких агентов общий средний RPS — sum(started) за общее окно от планового startAt до максимального generationStoppedAt, без drain; вклад агента использует его generationDurationUs. Для нормального старта generationDurationUs считается от планового монотонного start deadline, включая задержку пробуждения, до прекращения генерации.

Отчёт показывает requested RPS, observed start RPS, completion RPS, planned/scheduled/started/skipped/finished и признаки полноты отдельно. Missing batches, sticky measurementsLost и несогласованные суммы не заменяются нулями. Только после доставки всех последовательностей и проверки всех инвариантов результат может быть Complete. Во время Collecting результаты частичные.
