# LatencyStorm — план реализации MVP

Статус: план к реализации. Все этапы ниже пока не выполнены.

## Цель

Реализовать локально запускаемую платформу, которая создаёт заданную HTTP-нагрузку несколькими агентами, собирает результаты и формирует общий отчёт.

Контрольный сценарий: пользователь через API задаёт запрос к Demo Target, суммарную интенсивность 300 RPS и длительность 120 секунд. Control API распределяет нагрузку между тремя агентами. После завершения пользователь получает отчёт по фактической нагрузке, ошибкам и задержкам. Числа задают демонстрационный сценарий; достижимая производительность зависит от оборудования.

## Границы первой версии

В MVP входят:

- Один HTTP-запрос в сценарии: метод, URL, статические заголовки и необязательное тело.
- Постоянный суммарный RPS, длительность, таймаут запроса и максимальное число одновременных запросов на агенте.
- Создание, просмотр и запуск сценариев, просмотр состояния, ручная остановка.
- Один активный запуск на платформу и одно назначение на агент.
- Несколько агентов на Go, подключающихся к Control API по gRPC.
- Пакеты результатов через Kafka, история и отчёты в PostgreSQL.
- Счётчики запросов, коды ответов, ошибки, временной ряд нагрузки и p50/p95/p99.
- Обнаружение потери агента, ограниченное время работы без координатора, обработка дублей и неполных результатов.
- Метрики Prometheus и локальное окружение Docker Compose.

После MVP остаются веб-интерфейс, отдельный CLI, авторизация и многопользовательский режим, Kubernetes, несколько координаторов, автоматическое перераспределение нагрузки, многошаговые сценарии, переменные и извлечение данных из ответов, плавное изменение RPS, автоматическая остановка по порогам и сравнение запусков. Первая версия предназначена для локальной разработки и тестовых сервисов.

## Компоненты и структура репозитория

| Компонент | Технология | Ответственность |
| --- | --- | --- |
| Control API и встроенный координатор | C# / ASP.NET Core | Сценарии, запуски, назначения, gRPC-соединения и состояние агентов |
| Load Agent | Go | Генерация HTTP-нагрузки, локальные измерения, публикация результатов |
| Results Service | C# | Чтение Kafka, дедупликация, агрегация, API отчётов |
| Demo Target | Go | HTTP-сервис с управляемой задержкой и ошибками |
| PostgreSQL | Две базы в одном локальном экземпляре | Отдельное владение управляющими данными и результатами |
| Kafka | Один локальный брокер в режиме KRaft | Передача пакетов измерений |
| Prometheus | Отдельный контейнер | Метрики сервисов и генерации нагрузки |

Предлагаемая структура:

```text
src/
  control-api/
  load-agent/
  results-service/
  demo-target/
contracts/
  proto/
  events/
deploy/
  compose/
  prometheus/
tests/
  integration/
  e2e/
docs/
```

Control API и Results Service обращаются только к своим базам. Агент не обращается к PostgreSQL. Метрики Prometheus служат для наблюдения за работой системы, а история тестов хранится в базе результатов.

## Правила измерений

Эти правила нужно уточнить на этапе 1 и одинаково реализовать в Go и C#:

- `scheduled` — количество слотов запуска по расписанию до фактической остановки; полный запланированный объём хранится отдельно.
- `started` — запросы, переданные HTTP-клиенту; `skipped` — слоты, пропущенные из-за отставания или лимита конкурентности. После финализации `scheduled = started + skipped`.
- `finished` — запросы с любым терминальным исходом: HTTP-ответом, транспортной ошибкой, таймаутом или отменой. После завершения ожидания `started = finished`.
- HTTP-ошибки, транспортные ошибки, таймауты и отмены считаются отдельно. Для MVP HTTP 4xx/5xx считаются ошибочными ответами; автоматические ретраи и переходы по redirect отключены.
- Задержка измеряется от фактического старта запроса до чтения ответа или терминального сбоя. Отчёт отдельно показывает распределение завершённых HTTP-ответов и длительности неуспешных исходов; область расчёта перцентилей явно указана.
- Гистограмма имеет фиксированные границы в микросекундах и счётчик переполнения. Перцентили приблизительны в пределах разрешения buckets; отсутствие выборки возвращается как отсутствие значения.
- RPS запусков и RPS завершений различаются. Средний RPS запусков считается за окно генерации, без времени ожидания последних ответов.
- Отсутствующие измерения не заменяются нулями. Потерянные агенты и пакеты делают полноту отчёта явно ограниченной.

## Порядок работы и итоговая готовность

Этапы выполняются последовательно. На этапах 5–6 получается первый сквозной запуск на одном агенте; этап 7 добавляет распределение, этапы 8–10 завершают MVP. В каждом этапе реализуются необходимые проверки его поведения.

MVP готов, когда пользователь может локально запустить систему, выполнить тест на нескольких агентах, остановить его и получить сохранённый отчёт, в котором видны как результаты целевого сервиса, так и недостигнутая нагрузка и потери данных. Отдельные сценарии со сбоями должны подтверждать, что система прекращает нагрузку и корректно отмечает неполные результаты.
